1. Security-First Architecture: Principles and Approach
Design your AI development agent with defense-in-depth and zero-trust principles at its core. This means implementing multiple layers of security so that if one layer fails, others still protect the system. Zero-Trust Execution Environment: Treat the AI agent and all its outputs as untrusted by default. Just as modern system security isolates processes with different privilege levels, your agent should never get unrestricted access to critical resources without checks. Every action the AI plans – whether reading a file, executing code, or accessing the network – should be explicitly authorized by a policy before it runs. [cheatsheet....owasp.org]


Least Privilege & Allow-List Tools: Only enable the minimum set of capabilities (MCP commands/tools) the agent absolutely needs for development tasks. Avoid a catch-all “execute arbitrary command” tool config, which is dangerously over-permissive. Instead, define specific allow-listed commands and resources: [cheatsheet....owasp.org]

For example, rather than giving a blanket shell access, provide granular tools like a “read_file” command limited to certain project directories and with patterns like *.env, secret keys, or config files blocked. Similarly, a “run_tests” command might only execute your test script within a sandbox, and a “install_dependency” command might only allow installing pre-approved packages. [cheatsheet....owasp.org]
The Model Context Protocol (MCP) supports rich tool schemas for this purpose. Design each tool with clear parameters and safe defaults. E.g. an MCP file_reader tool can specify allowed file path patterns and operations (read vs write) at a policy level. By constraining inputs and outputs, you prevent the LLM from misusing tools for unintended actions. [cheatsheet....owasp.org]



Strong Isolation Boundaries: Establish clear trust boundaries in your architecture:

This ensures if the AI writes malicious or unstable code, it can’t harm the developer’s system. 4. Defining Agent Skills & Isolating Capabilities
To build a robust yet safe AI assistant, it’s helpful to break down its capabilities into distinct “skills” or phases – for example: Planning, Coding, Reviewing, Executing, and Remediating – and enforce separation of concerns among them. This limits the impact of mistakes or malicious outputs by any single step:


Planning Phase (Read-Only) – In this stage, the agent analyzes the task and possibly reads code or documentation to devise a plan. Keep planning logic isolated from direct execution. For instance, OpenCode has a dedicated “plan” agent that by default is not allowed to modify files or perform writes. You can adopt a similar model: during planning, enable only read/query tools (e.g. search project files, read docs) and explicitly deny any actions that alter state. This can be done via role-based permissions – e.g., define in your policy that when the agent is in “planner” mode, all write or exec commands are disabled. [yun123.io]


Code Generation Phase (Write) – Once a plan is approved by a human or by a higher-level policy, the agent proceeds to writing code. In this phase, the agent’s “write” or “edit” tools can be enabled to create or modify files in a controlled area (like a git feature branch or a temp directory). Here you should apply the secure coding guidelines: after generation, run automated checks (linters, Semgrep, etc.) on the diff. You might also employ an LLM-based code reviewer agent as a parallel check – e.g., Anthropic’s Claude Code has a plugin that runs 6 specialized review sub-agents in parallel to detect bugs or vulnerabilities in new code (with a confidence threshold to reduce false alarms). This kind of AI-on-AI review could catch logical issues that pattern-based tools miss. If any problems are found (failing tests, lint errors, or a security warning), the agent should enter a Remediation Phase where it fixes the issues (possibly after discussing with the user, depending on severity). [yun123.io]


Execution & Testing Phase (Restricted Execute) – Only after code passes static checks should the agent run it. At this point, transition to an “executor” context that has permission to launch code in the sandbox only, not on the host. The agent triggers the E2B/Docker environment and runs the necessary commands (compiling, running the software, executing test cases, etc.) in isolation. Keep this stage’s scope narrow: for example, the agent’s own process might have a “run_tests” command that behind the scenes calls a secure API to execute tests in the sandbox. The results (console output, test summaries) are then returned for analysis. Never allow the agent to directly invoke a compiler or run a server on the host. All such operations should be funneled through the sandbox interface. [AI Develop...cification | Txt]


Deployment Phase (High-Privilege or Out-of-Scope) – Actions like merging code to the main branch, deploying to production, or other persistent changes should always be treated as separate from the AI’s autonomous reach. Even if the agent can auto-generate a pull request or deployment script, you should require a human developer or a higher-level orchestrator to make the final call. One approach is to integrate with your CI/CD: the agent can open a pull request or trigger a CI job, but the pipeline will pause and notify a human for approval before actual deployment steps. This way, the AI assists with the heavy-lifting, but does not get carte blanche to alter live systems without oversight. [AI Develop...cification | Txt]


Implementing these phases may involve orchestrating multiple sub-agents or just one agent that follows a strict sequence. If using Claude Code, you can utilize its built-in structured workflow plugins (like the 7-stage feature-dev plugin) and insert your security checks at stage boundaries. For instance, after the “Architecture” stage and before “Implementation,” you could have a step that runs a design_review tool (maybe an LLM prompt that double-checks the plan against security guidelines). In Pi, you might script a sequence where the agent writes a plan to a markdown file first, pauses for user review, then continues to coding. Pi’s philosophy is that you, the developer, define the workflow – e.g., maintaining a TODO.md or plan file that the agent updates and follows. This is very flexible, but you must enforce the rules (like “don’t proceed to coding until a human marks the plan file as approved”). In OpenCode, you have a notion of distinct modes or agents (e.g., “plan” vs “build”) and even a quick toggle between them. You can use OpenCode’s role separation: e.g., configure the planning agent role to have only read/search tools, while the building agent can edit files. The general principle across all frameworks is to partition responsibilities and prevent any single agent step from doing everything – this limits the impact of a mistake or compromise in one part of the process. 5. Designing Secure MCP Commands & Permissions
Achieving security in an AI coding agent isn’t just about external tools – it’s also about how you design the agent’s command interface (MCP commands) and its internal policies. Here are best practices for command and skill design:


Use Declarative Command Schemas: Define each tool/skill with a narrow, well-defined schema. For example, instead of a generic run_command that accepts an arbitrary string (which the LLM could abuse), create specific commands like open_file(file_path), write_file(file_path, content), run_tests(test_suite_name), install_package(package_name). Each should have validation rules:

File paths can be constrained to a whitelist of directories or file types (and reject paths with .. or absolute references outside the workspace). [cheatsheet....owasp.org]
Package names can be checked against known package indices or a safe allow-list to prevent the AI from installing unknown software. (If the agent suggests a completely new or odd package, that’s a red flag for human review or extra verification via Snyk.)
Commands with side effects (like deleting files, modifying configs, making network calls) should be either entirely disallowed or require confirmation. Never rely on the AI to decide what’s safe – enforce it in code.



Permission Levels and Execution Modes: Implement a permission system for tools. Many agent frameworks already include this:

Claude Code’s config allows tagging each tool as “allow”, “ask”, or “deny” by default. For example, you can set the Bash execution tool to “ask” so that any time the agent wants to run a shell command, it pauses and asks the user for approval. Web access can be set to “deny” entirely if your agent doesn’t need it.
OpenCode uses a declarative ruleset: by default it allows most operations but will “ask” for things like potentially endless loops or external directory access, and you can customize these rules easily in a config file. It even parses shell commands with Tree-sitter to understand their impact (e.g., copying to an out-of-project directory triggers an external_directory check). We recommend adopting a similar ruleset approach: define patterns for risky actions (file paths, network calls, long-running loops) and handle them with ask/deny policies. [yun123.io]
Pi does not come with a permission system by default (it assumes “everything is allowed” unless you add restrictions). However, Pi’s extension hooks let you build this yourself. For instance, you can intercept the tool_call event in Pi and implement custom logic to confirm or block commands – an example extension (from Pi’s community) demonstrates blocking dangerous shell commands like rm -rf or sudo by intercepting the bash tool call and setting block: true if a regex matches. You can expand on this idea to cover any command you consider high-risk. [xda-developers.com], [yun123.io]



Human Confirmation Workflows: Some actions should trigger a confirmation even if they are allowed by policy. The OWASP guidance calls out a list of sensitive tools (like emailing, code deployment, database writes) that should require explicit user approval when invoked. Design your MCP commands so they can gracefully handle a “pending” state. For example, a command deploy_to_prod() might not directly execute; instead, it could create a deployment request and return a message like “Approval needed to proceed with production deployment. Please confirm.” The agent would then wait for a confirmation flag (which you could toggle via a special command or through an external system). This pattern keeps the human in control of critical steps. [cheatsheet....owasp.org]


Structured Outputs and Schema Validation: Whenever possible, have the AI output data in a structured format (JSON, YAML) for internal commands. This allows your agent’s code to validate the output against a schema before acting on it. For instance, if the AI proposes a batch of file changes as JSON (with file paths and diffs), your code can check that those paths are within allowed bounds and that the diffs don’t contain prohibited content (no secret tokens, no large deletions without corresponding additions, etc.) before applying them. This is analogous to how robust systems require well-formed transactions or use typed interfaces – don’t accept free-form instructions when you can enforce structure. [cheatsheet....owasp.org]


A combination of these strategies ensures the AI agent’s tool use remains within safe boundaries. The goal is to script the “rules of the road” so that even if the AI makes an unexpected decision, your wrapper will catch it. Many of these ideas are already exemplified by existing platforms – for instance, Claude Code’s security-guidance plugin uses predefined patterns to catch vulnerabilities in AI output (9 common vulns like weak encryption or hardcoded credentials). You can similarly maintain a list of “banned functions/APIs” (e.g., launching subprocesses, using eval, making network calls to non-whitelisted domains) and have the agent’s output scanner or code reviewer flag them immediately. 6. Context Management & Compression: “CTX vs RTK”
Lengthy conversations, large code outputs, and verbose tool results can quickly bust an LLM’s context window. Your agent will benefit from strategies to manage context and compress information without losing key details. You mentioned comparing a CTX plugin vs an RTK plugin – these represent two complementary approaches to context optimization:


“CTX” Context-Optimization Plugins: In frameworks like Claude Code, developers have created plugins (e.g. context-mode, LeanCTX) that embed intelligence in the agent to manage context. These plugins typically do things like:

Intercepting tool outputs and trimming or summarizing them before they are fed back into the prompt. For example, the context-mode plugin for Claude Code catches events like a bash command output and uses a 3-stage pipeline to strip ANSI characters, collapse repetitive logs (like long test outputs or git diff listings), and filter out irrelevant content. Only the condensed result (critical errors, summaries of output) is inserted into the LLM’s context. The full raw output can be stored in a local database in case it’s needed later, and the plugin can fetch relevant pieces on demand from this cache. [claudepluginhub.com]
Manage long conversation history by summarizing or selectively saving important info. Some context plugins save key points (goals, plans, recent code changes) to a local store, so that when the LLM’s context gets full and it “compacts” older messages, the plugin can re-inject critical context later to maintain continuity. [claudepluginhub.com]
These integrated context managers are powerful because they understand the agent’s behaviors and can tailor the compression. They often require using a specific agent platform (e.g. Claude Code’s plugin API). If you are using Claude Code, a context plugin is highly recommended to maximize the benefit of its 100k-token context – otherwise tool outputs will eat that up quickly. If you’re using OpenCode, there are community-driven plugins like “opencode-ctx” with similar goals (reducing Anthropic model context usage by ~50% by aggressive compaction). The downside is added complexity: you’ll need to run and possibly modify these plugins, and ensure they don’t interfere with your own agent logic. There’s also a small performance cost for processing outputs (e.g. the Claude context-mode plugin does add some overhead for its filtering pipeline). Proper testing is needed to ensure the summaries don’t accidentally omit critical info. Overall, though, these plugins can significantly cut down on token usage and prevent runaway context growth in long sessions.



RTK (Rust Token Killer) Proxy: RTK takes a different approach – instead of living inside the agent, it acts as a lightweight proxy that sits between the agent and the shell. When the agent issues a shell command, the RTK tool intercepts and rewrites the command to pre-process its output via a Rust binary. For example, if the agent wants to run git status, the RTK hook will silently transform it to rtk git status, so that the output gets passed through RTK’s filtering engine before the agent sees it. RTK is highly optimized (under 10ms added latency per command) and can reduce token usage dramatically – on average ~80% reduction of text, by removing irrelevant details and collapsing repetitiveness. It supports 100+ common commands out of the box, each with custom filters (for instance, grouping ls results, truncating long git diff to a summary, showing failing test names but not all passing test output, etc.). RTK is essentially a “dumb” but fast filter – unlike a context plugin, it doesn’t use an LLM or maintain long-term memory, it just applies heuristics to reduce text. This makes it easy to trust and deploy (small attack surface) and usable across different agents. In fact, there are integrations for OpenCode and other agents that simply require installing RTK and adjusting one setting to route all shell commands through it. If you’re using Pi or a custom setup, you could similarly incorporate RTK by prepending rtk to commands in your agent’s code or path. [pyshine.com] [github.com]


Which is better? In practice, many teams use both: RTK for quick wins on token savings, and a context plugin for deeper session management. If you have to choose one, consider your agent framework and needs:

If you stick with Claude Code, using the Context7 plugin plus Claude’s built-in compaction might suffice for documentation retrieval; adding the context-mode plugin will further help maintain long sessions without hitting token limits. This gives you a very advanced, fine-tuned context management but locks you more into the Claude ecosystem.
If you need a more agnostic solution or are using multiple agent platforms (Claude Code, OpenCode, Pi), RTK is a simple win. It’s open source, model-agnostic, and easy to add on top of any CLI agent to immediately cut down irrelevant token usage. It won’t handle all cases (for example, RTK focuses on CLI command outputs; it might not help compress large retrieved documents or lengthy interactive dialogues), but it excels at its niche. For many developers, RTK has become a default add-on to AI coding tools due to its significant boost in efficiency. You could start with RTK to tackle the most glaring token wastage (huge logs, etc.), and later introduce a fuller context management plugin as your agent grows more complex. 7. Leveraging Claude Code, OpenCode, and Pi – What to Utilize and What to Build
Finally, we assess how the AI coding agent platforms you’re using – Claude Code, OpenCode, and Pi – can support your security requirements, and where you’ll need to engineer custom solutions. Each of these has a distinct philosophy and feature set, which affects how much “built-in” security help they provide:


Claude Code (Anthropic) – Strengths: As an official product focusing on enterprise use, Claude Code is highly aligned with a security-first approach. It has a deny-by-default permission model (tools like shell commands are set to require user approval by default). It also supports extensive plugins and hooks – your PRD’s tools (Varlock, Trufflehog, etc.) can be integrated as plugins or via existing ones. For example, there is a community Varlock skill for Claude Code to manage environment secrets seamlessly. Claude Code ships with a Security Guidance plugin that flags 9 common vulnerability patterns (e.g. SQL injection) in code as the AI writes it. It also provides multi-agent collaboration out of the box, including a parallel code reviewer that uses multiple specialized “critique” agents to double-check generated code. These AI-side features can augment your traditional scanners – for instance, the Claude code-review agents might catch logical bugs or API misuses while Semgrep catches low-level issues. Challenges: Claude Code is not fully open source (Anthropic provides source-available code but with restrictions). It is also tied to using the Claude LLM by default – using other models requires extra setup and you may lose some of the deeply integrated features. If your organization is already using Claude extensively and values stability and built-in guardrails, this could be a good base. You would primarily focus on writing or configuring plugins for your security tools (most of which might already exist in the Claude ecosystem: e.g., Context7 by Upstash for RAG, Varlock skill, E2B integration plugin, etc.). [yun123.io] [claude.com]


OpenCode (by SST/Open Source) – Strengths: OpenCode is fully open-source (MIT) and designed for extensibility via plugins and custom tools. It has an advanced permission system using declarative rules (with sensible defaults that you can tweak in config) and even basic role separation (its “plan” agent cannot edit files, only the “build” agent can). OpenCode’s default settings are moderate (not as locked-down as Claude) but they do strike a balance: e.g., reading most files is allowed, but reading an .env file will prompt for confirmation by default. OpenCode includes unique features like LSP integration for deep code understanding and multi-model support; these can improve the agent’s accuracy and reduce risky guesswork by the LLM (since it can query a language server for, say, a function’s definition instead of blindly searching files). Community support is strong, with plugins available – e.g., an “Oh-My-OpenAgent” extension that adds 10 specialized sub-agents (though primarily for functionality and multi-model orchestration), and an RTK integration for OpenCode (via an rtk-for-opencode npm package). Being open-source, you can directly modify OpenCode’s codebase or contribute security features. Challenges: OpenCode doesn’t have the same level of built-in AI safety tools as Claude Code’s ecosystem. You’ll need to configure or add on scanners and possibly write custom plugins for things like Varlock or Trufflehog (if not already available). Also, the core is written in Go, so developing complex new plugins (beyond using existing ones) might have a higher learning curve if you’re more familiar with TypeScript/Python. However, for many needs, you can use the existing config and the MCP/ACP interfaces to connect external processes (for example, writing a wrapper that calls Snyk CLI when the agent tries to add a dependency). [yun123.io] [computingf...rgeeks.com]


Pi (open-source) – Strengths: Pi (formerly “Amp”) is essentially a minimalist kernel for a coding agent. It has only a few core tools (read, write, edit, bash, etc.) and leaves almost everything else up to the user’s extensions. The advantage here is complete control: you can implement your security features exactly to your specifications using Pi’s extension API (which allows hooking 20+ events in the agent’s lifecycle and adding or overriding commands). Pi can be thought of as a clean slate – it won’t impose any policy you don’t program. It’s also very model-agnostic and easily lets you switch between providers (OpenAI, Anthropic, local models, etc.) in mid-session, which can be useful if you want to, say, use a smaller/cheaper model for routine tasks and a more powerful one for security-critical reasoning. Notably, Pi’s lightweight design means less hidden prompt content – it doesn’t stuff a huge system prompt or memory into the conversation, which reduces the chance of hitting context limits and makes its behavior more predictable. Challenges: The flip side of Pi’s freedom is that nothing is pre-baked – “low default security” as noted in comparisons. Out of the box, Pi will happily run anything (it’s up to you to rein it in). You must implement all critical safeguards as custom extensions: e.g., writing a permission gate (though community examples like a permission-gate.ts extension can be a starting point) and integrating with external tools by writing new skills/commands. Pi’s philosophy is that users know their needs best, which resonates with a bespoke security setup – but be prepared to invest time in coding these controls. On the plus side, Pi’s simplicity means it’s easier to reason about what the agent is doing (no surprises from hidden rules or automatic plugin behaviors). In fact, you can use the AI itself to help write some of the extensions, but carefully review any AI-generated security code. [xda-developers.com], [yun123.io] [yun123.io] [xda-developers.com]


Summary of Trade-offs: If your priority is enterprise-grade security and minimal custom coding, Claude Code offers a strong starting point with built-in guardrails and a rich plugin ecosystem (for Varlock, Context7, etc.). If you need complete ownership of the codebase and flexibility, and you’re willing to implement the security mechanisms manually, Pi gives you that freedom (you essentially become the architect of its safety). OpenCode lies in the middle – it’s open-source and comes with some safety defaults and multi-agent structure, which you can extend, but it’s a larger system to grok than Pi. Many teams start with one of these frameworks as a backbone and modify it. Given that you’re already familiar with all three, you might even integrate their ideas: for example, using Claude Code’s structured workflow as inspiration, Pi’s extension hooks for custom controls, and OpenCode’s multi-model support and permission configs. No matter the foundation, the end-to-end architecture will look something like this: [claude.com]

User request → [Plan] → [Code] → [Scan] → [Test in Sandbox] → [Review] → [Approve & Deploy] (with potential loops back to planning or coding if scans/tests fail). Each transition is gated by policy checks or confirmations as needed.

Build confidence in each defense.
